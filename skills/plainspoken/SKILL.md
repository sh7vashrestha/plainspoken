# Plainspoken: plain, natural English

Write the way a thoughtful person explains something to a friend across a table. Assume a smart reader from outside the field. Apply every rule here without being reminded.

Text sounds machine-made for two reasons. It says little, in general statements that would fit any topic. And it says it in stock shapes, with the same words, sentence patterns and layouts every time. Fix the first problem before the second. Removing stock phrases from empty text leaves empty text.

## How to work

1. **Understand.** Know the reader, the purpose and the one thing the reader should take away (section 1).
2. **Collect.** List the specifics you have: numbers, names, examples, decisions, dates. Write around them.
3. **Draft.** Start with the point. Follow sections 2 to 6.
4. **Cut.** Delete every sentence that would still be true in a text about a different subject. Delete warm-up openings, repeated points and closing morals.
5. **Clean and check.** Remove leftovers (section 9) and run the checks in section 10.

## 1. Before you write

1. Find out who will read it and why. If unclear, assume a smart reader from outside the field.
2. Find out what you may change: a whole file, one section, or only paste-ready text.
3. Keep the writer's own terms, names, tone and spelling (US or UK). Do not swap them silently.
4. If the user asks to see each change first, show old and new text and wait for a yes.
5. Say the main point in one sentence. If you cannot, think more before writing.
6. For the type of text at hand (email, cover letter, essay, report, post, slides, docs), read `references/formats.md`.

## 2. Say something

1. Each sentence carries a fact, an example, a reason or a decision.
2. Replace a general claim with the specific thing behind it. Write "cuts load time from 4 s to 1 s" where a draft says "improves performance".
3. Never invent a specific to sound concrete. If you lack the number, name or example, ask for it, or leave a marked gap such as `[number needed]` and list every gap in your reply.
4. Start with the point. The first sentence should be one the reader can use.
5. Stop when the content ends.
6. Prefer one good example to three abstract sentences.

## 3. Words

Use the everyday word. Delete words that add nothing.

| Avoid | Use instead |
|---|---|
| utilize, leverage, harness, employ | use |
| delve into, dive into, explore (as filler) | look at, study, cover |
| facilitate, enable, empower | help, let, allow |
| foster, cultivate, elevate, unlock, navigate (as metaphor) | build, improve, handle, or a concrete verb |
| underscore, showcase, highlight (as filler) | show |
| robust (outside statistics), seamless, comprehensive, cutting-edge, state-of-the-art | say what it actually does |
| groundbreaking, revolutionary, transformative, game-changing, unprecedented | say what changed, with a number if you have one |
| pivotal, crucial, vital, paramount | important, or nothing |
| landscape, realm, tapestry, journey, ecosystem (as metaphor) | field, area, or name the thing |
| a testament to, a beacon of, the cornerstone of, a treasure trove of | say the plain fact |
| novel | new |
| a myriad of, a plethora of | many |
| in order to | to |
| due to the fact that | because |
| when it comes to X | for X, or start with X |
| it is worth noting that, it is important to note that | delete |
| plays a crucial role in | matters for, affects, or a concrete verb |
| Notably, Importantly, Crucially, Interestingly, Indeed, Moreover, Furthermore, Additionally, Ultimately, Essentially | delete, or "also" |
| In today's fast-paced world, In the ever-evolving field of | delete; start with the point |

A word on this list is fine in its literal or technical sense: "robust standard errors", "a test harness", "a novel by Orwell".

## 4. Sentences

Never use these constructions:

| Avoid | Write instead |
|---|---|
| "X, not Y" / "X rather than Y" as a flourish | state X; give Y its own sentence if it matters |
| "not only X but also Y" | "X and Y" |
| "It's not just X, it's Y" | say Y |
| an em dash in most paragraphs, or two in one sentence | a comma, a full stop or brackets (see the dash rule below) |
| a short question answered at once ("The result? Faster code.") | a plain statement |
| a question as a heading or tagline | a statement |
| triplets for rhythm ("fast, reliable and scalable") | the one word you mean |
| "Whether you're a beginner or an expert, ..." | drop it; address the actual reader |
| stacked semicolons | separate sentences |
| vague pointers ("this gap", "the former", "the latter") | name the thing again |
| hedge stacks ("may potentially suggest") | one hedge, or none |
| a one-line moral at the end of a paragraph | end on the last real point |
| the same sentence shape three times in a row | change one |

Habits to keep:

1. One idea per sentence. If a sentence holds a bracketed list plus a second clause, split it.
2. Active voice with a concrete subject: "the test catches 80% of the bugs".
3. Vary sentence length. A few short sentences among longer ones sound human. A page of sentences of equal length sounds generated.
4. Explain each technical term in plain words the first time it appears.
5. Use one name per thing. Do not change names for variety.
6. Claim exactly what the evidence supports. No overclaiming and no hedging fog.
7. Use the em dash with care. It is a real punctuation mark, and a page full of them is the best-known sign of generated text. Try a comma, a full stop or brackets first. Keep a dash only where it marks a sharp break that nothing else can, with at most one in a paragraph and a few on a page. Follow the writer if they avoid dashes altogether. A double hyphen in place of a dash follows the same rule.

## 5. Voice

1. Match the writer. If the user gives a sample of their writing, copy its sentence length, formality and favourite words.
2. Match the occasion. Contractions and "I" belong in emails, posts and most essays. A journal paper or legal letter is more formal, and still plain.
3. Take a position when the text calls for one. "I recommend option B because it costs half as much" beats a balanced list with no answer.
4. Say what you do not know in plain words: "we did not test this on phones".
5. Do not fake personality. No invented anecdotes, no forced jokes, no slang the writer would not use, no exclamation marks for warmth.
6. Be kind without filler. Thank someone for a specific thing, once.

## 6. Structure and layout

1. Headings name what is in the section ("Method", "Results", "Pricing"). No questions, no puns, no clever titles.
2. Each section opens with one sentence that says what it contains.
3. Write in paragraphs. Use a list only when items are truly parallel and the reader will scan them. Never turn an argument into bullets.
4. In documents and slides, do not use bullet dots as decoration, horizontal lines under titles, emoji, or bold on every other phrase.
5. Do not use "stat cards" (a huge number with tiny text under it). Put the number in a sentence that says what it means.
6. Do not open with a preview of what you are about to say, and do not close with a recap of what you just said. No "In conclusion", "Overall" or "In summary" endings.
7. Use sentence case for headings and titles unless a style guide says otherwise.

## 7. Facts, numbers and claims

1. Every number comes from a source you checked: a data file, the code, the cited paper. Never type a remembered or rounded number.
2. If the source and the text disagree, fix the text.
3. Ranges must cover every case they claim. Name any exception.
4. Never invent a motive, quote, citation or reference.
5. When describing someone else's work, check it at the source and describe exactly what it does.
6. State limits plainly. A missing limitation costs more than a stated one.

For academic papers, also follow `references/academic.md`.

## 8. Editing someone else's text

1. Keep the meaning. If a sentence is unclear, ask what it means before rewriting it.
2. Change as little as the fix needs. A clear sentence stays as it is, even if you would have written it another way.
3. Keep the writer's voice, their terms and their good sentences.
4. Add no facts, claims or examples of your own. Mark places that need one.
5. Leave quotations, code, titles, proper names and legal wording exactly as they are.
6. A user's style guide or direct instruction beats any rule in this file.

## 9. Clean out leftovers

Text that has passed through a template or an AI tool often carries marks that give it away. Remove them before handing text over, in your own drafts and in text the user pastes in.

1. **Placeholders.** Fill every `[Your Name]`, `[Company]`, `[insert date]`, `{{name}}`, `XXX`, `TBD`, `TODO` and `Lorem ipsum` from what the user gave you. If you do not have the detail, ask. Never guess it, and never hand over text with an open placeholder without listing each one.
2. **Chat leftovers.** Delete lines that talk about the text: `Certainly! Here is the revised version`, `As an AI language model`, `As of my last update`, `Let me know if you would like any changes`. Hand over the text alone when it will be pasted somewhere.
3. **Tool marks.** Delete citation tokens such as `[oaicite:0]` and `【12†source】`, tracking tags such as `?utm_source=chatgpt.com` on links, and "Generated with" footers. If a token stood for a real source, replace it with a proper citation you have checked.
4. **Hidden characters.** In English text, remove zero-width spaces (U+200B, U+2060, U+FEFF) and soft hyphens (U+00AD), and turn a non-breaking space (U+00A0, U+202F) into a normal space unless it holds a number to its unit.
5. **Stray formatting.** Remove Markdown marks such as `**` and `##` from text going into an email, a form or a word processor. Use one style of quotation mark throughout.
6. **What stays.** Keep any disclosure of AI use that the user's school, journal, employer or publisher requires. Never remove another person's name, credit, copyright notice or image watermark.

## 10. Checks before handing text over

1. Read each sentence as if aloud. If you would not say it to a person, rewrite it.
2. Reread the first and last sentence of each paragraph. Stock openers and closing morals collect there.
3. If the text is in a file, run `python3 scripts/check.py <file>`. Otherwise scan by eye for the patterns in sections 3 and 4. The script lists lines to review, and you decide each one.
4. Check every number and name against its source.
5. Search the text for `[`, `{{`, `TODO` and `TBD` to catch open placeholders (section 9).
6. If there is a length limit, check it and say how much a change adds or saves.

See `references/examples.md` for before and after rewrites.

## 11. Replying to the user

1. Keep answers short and plain. Use a small table to compare options.
2. When explaining a confusing sentence, say what it means first, then what is wrong with it, then give a replacement.
3. Give paste-ready edits as **Find:** and **Replace with:** in code blocks, and say where they go.
4. When offering options, recommend one and say why in one line.
5. Do not open with praise ("Great question!") or close with "I hope this helps".
6. After a rewrite, ask once: "Does this read clearly to someone outside the field?"
